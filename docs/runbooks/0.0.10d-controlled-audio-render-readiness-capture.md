# 0.0.10d Controlled Audio Render Readiness Capture

## Purpose

Run the existing non-physical readiness preflight exactly once and retain its successful Phase 7 report as canonical UTF-8 without BOM.

This wrapper prevents shell-redirection encoding differences and partial destination writes. It still does not authorize or execute physical audio output.

## Command

From a clean `main` checkout on Windows:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File .\tools\Save-ControlledWindowsPhysicalAudioRenderEvidenceReadiness.ps1 `
  -ExpectedCommit '<reviewed-40-character-main-SHA>' `
  -RuntimeDirectory 'C:\path\outside-repository\ffmpeg-runtime' `
  -FixturePath 'C:\path\outside-repository\controlled-audio-fixture.mkv' `
  -VideoRecordPath 'C:\path\outside-repository\accepted-video-record.txt' `
  -RenderEvidenceRecordPath 'C:\path\outside-repository\future-completed-record.txt' `
  -TerminalRenderRecordPath 'C:\path\outside-repository\future-terminal-record.txt' `
  -FailureRecordPath 'C:\path\outside-repository\future-failure-record.txt' `
  -ReadinessRecordPath 'C:\path\outside-repository\new-readiness-record.txt'
```

Optional operation bounds are the same as the readiness script and one-run helper:

- maximum decode operations: `128`;
- maximum delivery operations: `128`;
- fixture packet bytes: `65536`;
- observation hold: `1000 ms`;
- audio buffer: fixed at `100 ms`.

## Capture boundary

Before invoking readiness, the wrapper requires the readiness-record path to be:

- fresh as both a file and a directory name;
- repository-external;
- outside the external runtime directory;
- located in an existing parent directory;
- distinct from the runtime directory, fixture, accepted video record, and future completed, terminal, and failure paths.

The wrapper invokes only:

1. `Test-ControlledWindowsPhysicalAudioRenderEvidenceReadiness.ps1` exactly once;
2. the managed `--verify-controlled-windows-audio-render-readiness-record` preflight exactly once.

It does not invoke the one-run physical helper, render-evidence capture, direct physical command, delivery diagnostic, tone probe, decoded-slice probe, endpoint, decoder, scheduler, or native audio output.

## Private capture and validation

The readiness child stdout and stderr are redirected to private temporary files.

A successful capture requires:

- readiness exit code `0`;
- bounded non-empty stdout;
- bounded and empty stderr;
- exactly 27 non-empty readiness lines;
- reconstruction with canonical LF endings;
- UTF-8 encoding without BOM;
- create-new temporary-file semantics with no overwrite;
- successful managed strict readiness-record preflight using the exact reviewed commit, fixture digest, operation bounds, observation hold, and fixed audio buffer;
- a still-fresh destination immediately before promotion.

The validated temporary record is created in the destination directory and moved atomically to the requested path. A failure before the move leaves no readiness record.

## Successful result

Exit code `0` prints only:

```text
Result: ReadinessRecordCaptured
Readiness-Script-Executed-By-This-Command: True
Readiness-Record-Validated: True
Ready-For-Separate-Authorization: True
Physical-Run-Authorization-Granted: False
Physical-Runs-Executed-By-This-Command: False
Audio-Acceptance-Claimed: False
External-Binary-Or-Payload-Published: False
```

The output does not print the readiness-record path or retained report payload.

## Failure result

Exit code `1` prints a bounded validation category or the generic unexpected-capture category, followed by:

```text
Readiness record retained: Yes / No
Physical runs executed by this command: No
Readiness capture does not authorize physical execution.
```

`No` is reported for every failure before atomic promotion. `Yes` is possible only if promotion completed and a later status-output operation failed; the destination is never deleted or silently contradicted after successful promotion.

Raw readiness stderr, raw native output, exception messages, stack traces, local paths, and canonical report contents are not published.

## Independent review

Review the retained file with:

```powershell
dotnet .\src\Nova.ControlledWindowsRunner\bin\Release\net10.0\Nova.ControlledWindowsRunner.dll `
  --verify-controlled-windows-audio-render-readiness-record `
  --record 'C:\path\outside-repository\new-readiness-record.txt' `
  --expected-commit '<reviewed-40-character-main-SHA>' `
  --fixture-sha256 '32872B300286525F4EF97FEE3533E25419AC8E48BFD4BC2C4FD9545F071B1E15' `
  --max-decode-operations 128 `
  --max-delivery-operations 128 `
  --fixture-packet-bytes 65536 `
  --observation-hold-ms 1000 `
  --audio-buffer-ms 100
```

A captured and revalidated readiness record is evidence for an authorization decision only. It is not authorization.

## Required physical entrypoint

After a new explicit one-run authorization, the retained readiness record must be supplied to:

```text
tools/Run-ControlledWindowsPhysicalAudioRenderEvidenceWithReadiness.ps1
```

The underlying `Run-ControlledWindowsPhysicalAudioRenderEvidence.ps1` helper must not be invoked directly. The readiness-required entrypoint revalidates the record, confirms that its SHA-256 did not change during validation, rechecks clean `main` and fresh outcome paths, and only then invokes the existing helper once.

See `0.0.10d-controlled-audio-render-authorization-entrypoint.md` for the exact authorization statement and command template.

The historical one-run authorization at `4abadd280ceeae310b2528b6ea62f377211b1273` remains consumed.
