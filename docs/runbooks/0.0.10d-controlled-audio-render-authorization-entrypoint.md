# 0.0.10d Controlled Audio Render Authorization Entrypoint

## Purpose

Require a retained canonical readiness record and an exact explicit one-run statement before the existing controlled physical audio render helper can be invoked.

This entrypoint does not grant authorization. It enforces the mechanical conditions that must be present after a separate human authorization decision.

The underlying `Run-ControlledWindowsPhysicalAudioRenderEvidence.ps1` helper must not be invoked directly for a future run. Use only `Run-ControlledWindowsPhysicalAudioRenderEvidenceWithReadiness.ps1` after a new explicit authorization.

## Implementation-only restriction

Adding, reviewing, testing, or merging this entrypoint does not authorize execution.

Do not run:

- this entrypoint;
- the underlying one-run helper;
- the readiness or readiness-capture scripts;
- a render-evidence command;
- an ordinary helper or prior diagnostic;
- a tone or decoded-slice probe;
- paired verification.

## Required inputs

The entrypoint requires the same reviewed identities and bounds as the readiness record and physical helper, plus:

- `ReadinessRecordPath`: an existing canonical Phase 7 readiness record retained outside the repository and runtime directory;
- `AuthorizationStatement`: exactly:

```text
I explicitly authorize exactly one controlled physical audio render run.
```

The literal statement is only an accidental-invocation guard. It is not a substitute for a new explicit authorization from the reviewer/operator.


Retain the reviewed defaults unless the separate authorization explicitly says otherwise:

- maximum decode operations: `128`;
- maximum delivery operations: `128`;
- fixture packet bytes: `65536`;
- observation hold: `1000 ms`;
- audio buffer: fixed at `100 ms`.

## Pre-helper gates

Before it can invoke the physical helper, the entrypoint requires:

- Windows;
- the exact authorization statement;
- checked-out branch `main`;
- `HEAD` equal to the approved commit before and after readiness validation;
- a clean tracked and untracked working tree before and after readiness validation;
- an existing readiness record;
- fresh completed, terminal, and failure paths;
- existing parents for all three future outcome paths;
- runtime, fixture, video, readiness, completed, terminal, and failure paths pairwise distinct;
- every path repository-external;
- the readiness record outside the runtime directory;
- successful solution restore and controlled-runner Release build;
- successful strict managed readiness-record preflight using the exact commit, fixture digest, operation bounds, observation hold, and fixed audio buffer;
- an unchanged readiness-record SHA-256 across managed validation;
- all three future outcome paths still fresh immediately before helper invocation.

The entrypoint invokes the existing helper exactly once only after all these gates succeed.

## Process-output boundary

Git, dotnet, readiness-preflight, and helper stdout/stderr are captured in private temporary files and bounded before reading.

The entrypoint relays the already bounded and sanitized helper output only when:

- the process output remains within bounds; and
- the helper returns one of its reviewed exit codes: `0`, `1`, or `2`.

Unexpected process results are replaced with a bounded authorization-gate failure.

## Failure before helper invocation

A gate failure before helper invocation prints only a bounded category followed by:

```text
Physical helper invoked: No
Physical runs executed by this command: No
This gate failure does not authorize physical execution.
```

No physical command is reached.

## Failure after helper invocation

Once the helper has been invoked, the entrypoint never claims that no physical run occurred. An unexpected wrapper-level failure prints:

```text
Physical helper invoked: Yes
Physical run completion established: No
Do not rerun this command.
```

The retained completed, terminal, child-failure, or helper-failure record must be reviewed before any further decision.

## Authorization boundary

A validated readiness record means the reviewed environment was ready when captured. The exact statement means the operator copied the reviewed invocation guard. Neither fact independently grants authorization.

A physical invocation still requires all of the following:

1. a separately merged commit;
2. final-head and post-merge CircleCI success;
3. a newly captured and independently revalidated readiness record for that exact commit and bounds;
4. new repository-external completed, terminal, and failure paths;
5. a new explicit one-run authorization;
6. execution through this readiness-required entrypoint exactly once.

The historical authorization at `4abadd280ceeae310b2528b6ea62f377211b1273` remains consumed and cannot be reused.
