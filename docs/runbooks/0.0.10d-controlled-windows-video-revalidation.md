# 0.0.10d Controlled Windows Video Revalidation

## Purpose

Repeat the Phase 5 physical video run after the decoded packet-time-base, production presentation-origin, bounded operator-observation, and single-record preflight fixes. This run must use the exact approved external FFmpeg runtime and the retained controlled fixture. It must not start the audio run or paired-record verification.

## Fixed fixture identity

- Identity: `pcn-0.0.10b-controlled-h264-aac-flv-v1`
- Bytes: `66,939`
- SHA-256: `32872B300286525F4EF97FEE3533E25419AC8E48BFD4BC2C4FD9545F071B1E15`
- Media: H.264 320×240 at 10 fps and AAC-LC 48 kHz stereo

The fixture and FFmpeg runtime remain outside the repository. The generated record must also be written outside the repository.

## Preconditions

1. Use Windows 11 with a visible interactive desktop.
2. Check out `main` at the explicitly approved post-merge commit.
3. Keep the Git working tree clean.
4. Use the same approved runtime directory and retained fixture used by the earlier Phase 5 runs.
5. Choose a new repository-external record path; the helper refuses to overwrite an existing record.

## Command

From the PeerCast Nova repository root:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\Run-ControlledWindowsPhysicalVideo.ps1 `
  -ExpectedCommit <APPROVED_MAIN_SHA> `
  -RuntimeDirectory 'C:\path\to\approved-ffmpeg-bin' `
  -FixturePath 'C:\path\to\pcn-0.0.10b-controlled-h264-aac-flv-v1.flv' `
  -RecordPath 'C:\path\outside-repository\pcn-0.0.10d-video-record.txt'
```

The helper performs these checks before native activation:

- Windows host;
- branch exactly `main`;
- exact expected commit;
- clean Git working tree;
- runtime, fixture, and record paths outside the repository;
- exact fixture byte count and SHA-256;
- successful solution restore and Release runner build.

It then executes exactly one `video` physical run through `Nova.ControlledWindowsRunner`, requests an explicit three-second observation hold after successful delivery, writes only the canonical sanitized stdout record as UTF-8, revalidates the record envelope and fixed identities, and confirms that the repository stayed clean.

When the physical command exits successfully, the helper immediately invokes the verify-only single-record preflight. The preflight reads the external record through the canonical bounded UTF-8 reader, parses the complete fixed schema, and submits it to the same independent run-set admission boundary used by paired verification. It starts no runner, runtime, fixture, decode, or physical output. The helper succeeds only when the report states:

- `Result: VideoAccepted`
- `Expected-Kind: Video`
- `Record-Accepted: True`
- `Physical-Runs-Executed-By-This-Command: False`

The temporary preflight report is removed. The canonical physical record remains repository-external.

The observation hold can be overridden for diagnostics with `-ObservationHoldMilliseconds`, but it must remain within 0 through 30,000 milliseconds. During the hold, no additional decode, delivery, retry, scheduler operation, native output operation, or evidence mutation occurs. The presented output lifecycle and application-owned window remain alive only for operator inspection.

## Required result

A successful deterministic run has all of the following in the canonical record:

- `Kind: Video`
- `Result: Completed`
- `Evidence: Accepted`
- `Delivery-Attempts: 1`
- `Delivered: 1`
- `Retained-WouldBlock: 0`
- positive native video attempt and acknowledgement evidence through the admitted lifecycle snapshot
- `Runner-State: Stopped`
- `Lifecycle-State: Disposed`
- borrowed window and dispatcher preserved
- `External-Binary-Or-Payload-Published: False`

The helper must also print:

```text
Canonical video preflight: Accepted
```

During the explicit observation hold, inspect the controlled output window. After the command closes, answer exactly one operator observation:

```text
Video visible: Yes
```

or

```text
Video visible: No
```

The operator observation is supporting evidence and does not replace deterministic admission.

## Failure handling

On any nonzero exit, retain the canonical record outside the repository and report it together with the operator observation. Do not add temporary instrumentation, change the fixture, widen timing limits, synthesize timestamps, retry delivery, start audio, or run paired verification until the new terminal boundary is diagnosed.

If the physical command exits successfully but canonical preflight rejects the record, treat the preflight rejection as the new terminal boundary and do not start audio.

If deterministic video evidence is accepted but the window is not visibly rendered, stop before audio and diagnose the visible-output contradiction.
