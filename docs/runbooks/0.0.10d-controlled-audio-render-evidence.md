- ordinary helper: three attempts, two deliveries, noise-like unrecognizable audio;
- exact delivery diagnostic: four `AudioDelivered` results, accepted aggregate evidence, no audible sound.

## Helper gates

Before starting the physical child, the helper requires:

- Windows;
- checked-out branch exactly `main`;
- `HEAD` exactly equal to `ExpectedCommit`;
- a clean tracked and untracked working tree;
- repository-external runtime, fixture, video record, completed-evidence record, terminal record, and failure record paths;
- a retained fixture of exactly `66,939` bytes and the approved SHA-256;
- fresh completed-evidence, terminal, and failure paths;
- video, completed-evidence, terminal, and failure record paths pairwise distinct;
- an accepted canonical video record.

Native `git` and `dotnet` stdout/stderr are redirected to private temporary files and deleted after each command. Native execution temporarily uses `ErrorActionPreference = Continue` only inside that boundary and restores the prior value immediately. Raw native stderr is never published or retained. Only explicitly required canonical stdout is parsed.

## Exclusive managed outcomes

After the child exits, exactly one of these combinations is permitted:

| Capture exit | Retained path | Meaning |
|---:|---|---|
| `0` | completed-evidence only | completed and accepted technical render evidence |
| `1` | terminal only | reviewed bounded terminal evidence; completion not established |
| `2` | sanitized failure only | no valid completed or terminal record |

Any contradictory file/exit combination is rejected. The helper never converts a terminal record into completed evidence or an audio-acceptance claim.

### Terminal record

The terminal path requires a three-line canonical envelope:

```text
PEERCAST-NOVA-CONTROLLED-WINDOWS-AUDIO-TERMINAL-RENDER 1
Record: <canonical bounded JSON>
END-PEERCAST-NOVA-CONTROLLED-WINDOWS-AUDIO-TERMINAL-RENDER
```

The managed child has already applied the strict terminal codec. The helper applies a defensive bounded envelope and identity gate requiring:

- schema version `1` and milestone `0.0.10d Phase 6`;
- exact runtime and fixture identity;
- one reviewed result: `DecodeRejected`, `DeliveryRejected`, `EvidenceRejected`, `Cancelled`, or `Faulted`;
- `RunnerState = Stopped` and `LifecycleState = Disposed`;
- exact observation-hold and audio-buffer durations;
- pre-cleanup and post-stop delivery, WASAPI, and native evidence objects;
- `PhysicalRunStarted = true`;
- `PhysicalRunCompleted = false`;
- `CompletedRenderEvidenceEstablished = false`;
- `AudioAcceptanceClaimed = false`;
- `ExternalBinaryOrPayloadPublished = false`.

A valid terminal record makes the helper exit `1`. It is retained evidence of where the run terminated, not proof of audible or accepted audio, and not authorization to rerun.

## Failure behavior

Any failed child, invalid UTF-8 output, malformed record, identity mismatch, path contradiction, contradictory outcome combination, or integration failure is terminal.

- no automatic retry;
- no helper rerun;
- no raw stdout or stderr publication;
- no alternate endpoint;
- no timing, buffer, fixture, or operation-bound change;
- no additional probe;
- no paired verification.

When available, the current Phase 6/version 5 sanitized child failure record retains only bounded child-exit availability, the normalized exit value when available, stdout/stderr byte counts, the last exact allowlisted native-audio stage or `None`, one exact allowlisted controlled run result or `None`, one exact allowlisted terminal-record rejection category or `None`, and whether a child-process result was captured. A result is retained only when the private stdout is exactly one canonical managed result line. A terminal-record rejection is retained only from exactly one canonical managed stderr marker. Unknown, additional, duplicate, malformed, or noncanonical output fails closed to `None`. The record explicitly states that neither canonical completed nor terminal evidence was produced, raw output was not published, physical completion was not established, and audio acceptance was not claimed. Unknown stage text, paths, and other stderr content are not retained. Canonical legacy version 4, version 3, and version 2 records remain readable with an effective terminal-record rejection of `None`; version 3 and version 2 also have an effective controlled run result of `None`, and version 2 has an effective stage of `None`.

After the external failure path passes every existing path gate, any terminal helper failure that has produced none of the completed, terminal, or sanitized child failure records atomically retains a separate bounded helper-failure record:

```text
Result: HelperFailure
Failure-Phase: <bounded helper phase>
Failure-Category: <ValidationFailure or bounded exception category>
Canonical-Render-Evidence-Record-Produced: False
Canonical-Terminal-Render-Record-Produced: False
Sanitized-Child-Failure-Record-Produced: False
Physical-Run-Completion-Established: False
Raw-Exception-Published: False
Raw-Native-Stderr-Published: False
Audio-Acceptance-Claimed: False
External-Binary-Or-Payload-Published: False
```

Validation failures are identified with an internal exception marker rather than matching arbitrary exception-message prefixes. The marker and exception category are resolved through the complete `InnerException` chain so Windows PowerShell wrapping does not erase their identity.

The records do not contain exception messages, stack traces, command lines, local paths, native stderr text, device identity, handles, pointers, HRESULTs, packets, payloads, or samples. If failure happens before the external failure path is authorized, only the bounded phase/category is written to stderr and no file is created.

After either a completed or terminal technical record, answer separately:

```text

```

`Yes` requires clearly recognizable retained-fixture sound. A click, noise-like transient, silence, or uncertainty is `No`.
