The run uses the exact approved external FFmpeg runtime and the same retained controlled fixture. It produces one separate repository-external audio record and does not perform paired-record verification.

## Command

From the PeerCast Nova repository root:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\Run-ControlledWindowsPhysicalAudio.ps1 `
  -ExpectedCommit <APPROVED_MAIN_SHA> `
  -RuntimeDirectory 'C:\path\to\approved-ffmpeg-bin' `
  -FixturePath 'C:\path\to\pcn-0.0.10b-controlled-h264-aac-flv-v1.flv' `
  -VideoRecordPath 'C:\path\outside-repository\pcn-0.0.10d-corrected-video-record.txt' `
```

Use the default `ObservationHoldMilliseconds=1000`, `MaximumDecodeOperations=128`, `MaximumDeliveryOperations=128`, and `FixturePacketBytes=65536` unless a new diagnosed boundary requires a reviewed change.

## Gate order

The helper performs these steps in order:

1. validate Windows, exact clean `main`, external paths, distinct records, fixture bytes, and fixture SHA-256;
2. restore the solution and build the dedicated Release runner;
3. submit the existing video record to verify-only single-record preflight;
4. reject before native audio activation unless the result is `VideoAccepted`;
5. invoke the `net10.0` managed child-capture command exactly once;
6. let that command execute at most one controlled physical `audio` run and
   atomically retain either a canonical audio record or sanitized failure record;
7. on physical success, submit the audio record to single-record preflight;
8. reject unless the result is `AudioAccepted`;
9. confirm the repository remained clean.

The video gate and audio preflight start no runner, runtime, fixture, decode, or physical output. Their reports contain no record paths.

## Audio observation hold

The helper requests a default one-second observation hold after the single audio delivery. The hold does not repeat, synthesize, stretch, resubmit, or regenerate audio. It keeps the existing WASAPI lifecycle alive long enough for the already accepted buffer to reach the endpoint before cleanup.

The selected decoded audio item may be brief. Audible observation remains supporting evidence and cannot replace deterministic admission.

## Required deterministic result

A successful canonical audio record contains:

- `Kind: Audio`;
- `Result: Completed`;
- `Evidence: Accepted`;
- `Delivery-Attempts: 1`;
- `Delivered: 1`;
- `Retained-WouldBlock: 0`;
- positive native audio write and start acknowledgement evidence through the admitted lifecycle snapshot;
- `Runner-State: Stopped`;
- `Lifecycle-State: Disposed`;
- borrowed window and dispatcher preserved;
- `External-Binary-Or-Payload-Published: False`.

The helper must also print:

```text
Video record gate: Accepted
Canonical audio preflight: Accepted
```

After the command closes, record exactly one supporting observation:

```text
Audio audible: Yes
```

or

```text
Audio audible: No
```

## Failure handling

On any nonzero exit, retain the canonical audio record if one was produced and report the first terminal boundary. Do not replace the accepted corrected video record, mutate the fixture, retry or redeliver, widen timing limits, synthesize audio, add instrumentation, or start paired verification until the boundary is diagnosed.

If the video gate rejects, no physical audio output is attempted. If the audio physical command succeeds but audio preflight rejects, treat preflight rejection as the terminal boundary. If deterministic audio evidence is accepted but no audio is audible, retain both facts separately and stop before paired verification.

## First-run failure and corrected selection gate

The first physical audio attempt on clean main
`36ff2d616965975f9d42879cfbf4e23ded99ace1` passed the video gate as
`VideoAccepted`, performed two decode operations, and transferred an audio frame.
Its only delivery attempt returned `DeliveryRejected`, with delivered count `0`,
retained WouldBlock count `0`, and no native audio evidence. Audio preflight and
operator observation were not executed. The borrowed-owner `False` fields were
unassessed because of the early terminal result, not evidence of an owner
contradiction. WASAPI reachability was not established.

The cause was the generation scheduler's initial video preference while both
media kinds remained queued from fixture replay. Controlled lifecycle creation
now maps the requested run kind to the scheduler's first successful reservation:
video for a video run and audio for an audio run. Empty and cancelled reservation
attempts do not consume this preference. After the first reservation, the existing
caller-driven preference and alternating selection resume. The bounded controlled
settings remain capacity `16`, maximum owned bytes `64 MiB`, and `DropOldest`.

Do not infer physical audio success from this correction. Re-run the gated audio
helper once only after its merge is approved. Until that corrected run completes,
do not run audio preflight, request audible observation, or run paired
verification.

The diagnostic helper requires a new repository-external failure path in


The audio and failure paths must not exist and must differ from each other and
from the video record. The helper runs the physical child at most once. It stores
a complete canonical audio envelope at `AudioRecordPath` or, if none is
available, stores only the fixed sanitized failure envelope at
`FailureRecordPath`. It never stores raw stderr. The failure envelope contains
only output byte counts, the signed and eight-digit hexadecimal child exit code,
an allowlisted stderr classification, and the final exact allowlisted native
audio stage.

This command is a diagnostic run. Do not use it as final physical audio
acceptance, request audible observation, or start paired verification.

## Windows PowerShell 5.1 compatibility

The supported invocation remains:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\Run-ControlledWindowsPhysicalAudio.ps1 ...
```

Do not require PowerShell 7 or `pwsh`, and do not make a persistent execution
policy change. The bypass is scoped to the helper process.

On clean main `4968e40f801f72bb06a71007a04a47911b6ac377`, the Release runner
build succeeded but the helper failed before physical-child start. It created
neither audio nor failure record. Physical output, audio preflight, audible
observation, and paired verification were not run. The failure was the helper
host boundary: Windows PowerShell 5.1 cannot host the `net10.0` CLI assembly or
its modern process setup contract. This result supplies no WASAPI evidence and
does not refute PR #112.

The helper no longer loads a managed assembly or constructs the physical
process. After video preflight it invokes
`--capture-controlled-windows-audio-child` once through `dotnet`. The managed
command uses the same runner assembly to start one audio physical child with
fixed native-stage diagnostics. It passes paths through `ArgumentList`, drains
stdout and stderr concurrently as bytes, and atomically creates exactly one
final record:

- exit `0`: canonical audio record, child exit `0`;
- exit `1`: canonical audio record, child nonzero;
- exit `2`: no canonical output and one sanitized failure record;
- exit `3`: capture configuration or integration failure, with no incomplete
  final record.

Raw stderr is never stored or written to parent stdout. A canonical nonzero
record is retained without audio preflight. A sanitized failure record is
printed in full by the helper and then treated as the terminal boundary.
