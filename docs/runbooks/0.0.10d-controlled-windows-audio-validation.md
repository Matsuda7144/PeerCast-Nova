# 0.0.10d Controlled Windows Audio Validation

## Purpose

Execute the Phase 5 physical audio run only after the independently retained video record passes canonical single-record admission. The run uses the exact approved external FFmpeg runtime and the same retained controlled fixture. It produces one separate repository-external audio record and does not perform paired-record verification.

## Fixed identities

- Runtime build: `btbn.ffmpeg.20260721.win64.lgpl-shared`
- Fixture identity: `pcn-0.0.10b-controlled-h264-aac-flv-v1`
- Fixture bytes: `66,939`
- Fixture SHA-256: `32872B300286525F4EF97FEE3533E25419AC8E48BFD4BC2C4FD9545F071B1E15`
- Media: H.264 320×240 at 10 fps and AAC-LC 48 kHz stereo

The runtime, fixture, accepted video record, generated audio record, and all temporary command output remain outside the repository.

## Preconditions

1. Use Windows 11 with an interactive audio session and the intended default output endpoint available.
2. Check out `main` at the explicitly approved post-merge commit.
3. Keep the Git working tree clean.
4. Use the same approved runtime and retained fixture used by the video run.
5. Supply the repository-external video record produced by the accepted video helper run.
6. Choose a new repository-external audio record path.

## Command

From the PeerCast Nova repository root:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\Run-ControlledWindowsPhysicalAudio.ps1 `
  -ExpectedCommit <APPROVED_MAIN_SHA> `
  -RuntimeDirectory 'C:\path\to\approved-ffmpeg-bin' `
  -FixturePath 'C:\path\to\pcn-0.0.10b-controlled-h264-aac-flv-v1.flv' `
  -VideoRecordPath 'C:\path\outside-repository\pcn-0.0.10d-video-record.txt' `
  -AudioRecordPath 'C:\path\outside-repository\pcn-0.0.10d-audio-record.txt'
```

## Gate order

The helper performs these steps in order:

1. validate Windows, exact clean `main`, external paths, fixture bytes, and fixture SHA-256;
2. restore the solution and build the dedicated Release runner;
3. submit the existing video record to verify-only single-record preflight;
4. reject before native audio activation unless the result is `VideoAccepted`;
5. execute exactly one controlled physical `audio` run;
6. retain the canonical audio record outside the repository;
7. on physical success, submit the audio record to single-record preflight;
8. reject unless the result is `AudioAccepted`;
9. confirm the repository remained clean.

The video gate and audio preflight start no runner, runtime, fixture, decode, or physical output. Their reports contain no record paths.

## Audio observation hold

The helper requests a default one-second observation hold after the single audio delivery. The hold does not repeat, synthesize, stretch, resubmit, or regenerate audio. It keeps the existing WASAPI lifecycle alive long enough for the already accepted buffer to reach the endpoint before cleanup.

The hold may be overridden with `-ObservationHoldMilliseconds` in the inclusive range 0 through 30,000 milliseconds. The fixture's selected decoded audio item may be brief; audible observation remains supporting evidence and cannot replace deterministic admission.

## Required deterministic result

A successful canonical audio record contains:

- `Kind: Audio`
- `Result: Completed`
- `Evidence: Accepted`
- `Delivery-Attempts: 1`
- `Delivered: 1`
- `Retained-WouldBlock: 0`
- positive native audio write and start acknowledgement evidence through the admitted lifecycle snapshot
- `Runner-State: Stopped`
- `Lifecycle-State: Disposed`
- borrowed window and dispatcher preserved
- `External-Binary-Or-Payload-Published: False`

The helper must also print:

```text
Video record gate: Accepted
Canonical audio preflight: Accepted
```

After the command closes, record exactly one supporting observation:

```text
Audio audible: Yes
```

or

```text
Audio audible: No
```

## Failure handling

On any nonzero exit, retain the canonical audio record if one was produced and report it together with the operator observation. Do not replace the accepted video record, mutate the fixture, retry hidden delivery, widen timing limits, synthesize audio, or start paired verification until the terminal boundary is diagnosed.

If the video gate rejects, no physical audio output is attempted. If the audio physical command succeeds but audio preflight rejects, treat preflight rejection as the terminal boundary. If deterministic audio evidence is accepted but no audio is audible, retain both facts separately for review.
